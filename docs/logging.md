# Logging and observability

P'tit Pote uses a shared Winston logger for HTTP requests, Discord interaction
handlers, Gateway events, MikroORM output, command registration, and process
exceptions.

## Runtime architecture

- `src/logger.ts` creates the shared `logger` export.
- `src/api.ts` assigns a UUID request ID to every Express request, returns it as
  `x-request-id`, and forwards Morgan access logs to `logger.http('request')`.
- `src/mikro-orm.config.ts` replaces MikroORM's default logger with a Winston
  bridge. SQL queries are emitted as `info` messages named `new sql query`.
- `src/gateway.ts` and `src/gateway/*` use the same logger for Gateway
  lifecycle, payload, and Discord dispatch diagnostics.
- `src/register.ts` logs slash-command registration payloads and outcomes. Run it
  only through the documented registration workflow.

Each log event is JSON formatted with common fields:

| Field   | Meaning                                      |
| ------- | -------------------------------------------- |
| `ts`    | Winston timestamp.                           |
| `lvl`   | Winston level such as `info`, `http`, `debug`. |
| `logid` | Per-log UUID generated by `src/logger.ts`.   |
| `v`     | Package version from `npm_package_version`.  |
| `msg`   | Message passed to the logger.                |

Structured metadata is appended to the JSON object. For HTTP interactions, use
`reqId` to correlate the Morgan access log with command, CTA, or modal handler
logs.

Example access log:

```json
{
  "ts": "2026-08-09T09:02:07.769Z",
  "lvl": "http",
  "logid": "ec30c3b2-3f81-4cc0-9ff7-87af83f42891",
  "v": "1.7.7",
  "msg": "request",
  "method": "POST",
  "url": "/interactions",
  "status": 200,
  "duration": 21.5,
  "reqId": "4018df87-e547-49bb-926e-e798cb4d19c0"
}
```

## Levels and destinations

`LOG_LEVEL` controls both stdout and the combined rotating file transport. The
default is `http`, which includes request, info, warning, and error logs. Use
`LOG_LEVEL=debug` for interaction payloads, Gateway lifecycle traces, and Zod
validation details.

Winston writes these files relative to the Node.js process working directory:

| File pattern                            | Contents                         |
| --------------------------------------- | -------------------------------- |
| `logs/ptitpote-combined-%DATE%.log`     | Normal app logs up to `LOG_LEVEL`. |
| `logs/ptitpote-exceptions-%DATE%.log`   | Uncaught exceptions.             |
| `logs/ptitpote-rejections-%DATE%.log`   | Unhandled promise rejections.     |

File transports rotate daily, compress archives, cap each file at `20m`, and
retain files for `7d`.

Production Compose mounts `${PWD}/logs` into `/app/logs` for both the `api` and
`gateway` containers. The GHCR image expects the same writable path when run
directly:

```bash
mkdir -p logs
docker run --env-file .env -v "$PWD/logs:/app/logs" \
  ghcr.io/gtspray/ptitpote:<version>-amd64 both
```

`make logs` follows Docker stdout for the `api` and `gateway` containers and
pipes JSON lines through `jq`. Rotating files are still useful for retention
across container restarts.

## Troubleshooting

- **No file logs are written:** confirm the `logs/` directory exists and is
  writable by the container user. File transport failures are surfaced on stdout
  as JSON with `msg: "Winston transport error (...)"` and `err.code` such as
  `EACCES` or `ENOENT`.
- **A Discord request failed but the user only has an error response:** ask for
  the `x-request-id` response header, then search logs for that `reqId`.
- **Gateway behavior is missing:** run with `LOG_LEVEL=debug` and search for
  Gateway messages such as `GatewaySocket.connect`, `opened connection`,
  `gateway error`, or `try to resume connection`.
- **Database output is too noisy:** MikroORM debug logging is enabled in
  `src/mikro-orm.config.ts`, so SQL query messages appear at `info` level. Lower
  verbosity requires a code change, not just an environment change.

## Developer conventions

- Import the shared logger from `src/logger.ts`; do not create ad hoc Winston or
  console loggers in feature code.
- Prefer structured metadata (`logger.info('message', { reqId, pollId })`) over
  string interpolation so logs remain searchable.
- Include `reqId` in logs produced during HTTP interaction handling.
- Do not log secrets, Discord tokens, authorization headers, or raw environment
  values. Raw interaction payloads are debug-only and should stay out of normal
  `http` or `info` logs.
- Let Winston handle `Error` objects where possible; `errors({ stack: true })`
  preserves stack traces in structured output.
